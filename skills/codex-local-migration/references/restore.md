# Destination recovery and acceptance

This is a version-aware local recovery procedure. The bundled helper exports and verifies archives. A successful archive check establishes receipt and integrity. Live integration depends on the installed desktop app, CLI, account and workspace ownership, and history layout.

## Prepare the destination

1. Verify the received native ZIP with `native_bundle.py verify`. Extract reviewed bundles and retain the ZIPs. Verify the project files and any separate supplements. Use Downloads as the receiving location. Move the extracted project package as a unit to a long-term folder such as **Documents → Codex Projects**, keeping attachments and path maps in their relative locations.
2. On the destination Mac, open **Projects → + → Local** in Codex and select the inner folder containing the project files as its primary source. For example, in `Research-transfer/Research`, choose `Research`. Reuse an existing local project whose primary path already matches. If it points to Downloads or to the outer package folder, open its **⋯ → Edit project** menu and change the primary source to the inner folder at the new location. Save and confirm the path before restoring project membership. If the agent cannot operate the sidebar, have the user perform this step and confirm the visible project name and folder. Verification and isolated rehearsal can proceed before this step. Check the destination project and path before assigning recovered chats to it. [Local project setup example](https://learn.chatgpt.com/training/codex-lab/index.html?step=project)
3. Check for the same original IDs in the destination's active and archived inventory. For an ID already present, determine whether it has the same lineage, a newer continuation, or conflicting content. Keep both exports and resolve the collision explicitly before any write.
4. Compare the app and bundled CLI versions, schema and migration metadata, and account and workspace. Respect account-ownership fields. Treat unsupported or substantial version differences as an unresolved compatibility issue until tested in a copy. Leave target credentials in their normal store.
5. For a matching saved Git repository on a connected host, consider the product's chat handoff. For viewing on another device while the old host is online, remote access may be sufficient. Choose local migration only when the user needs the history on the destination itself. [OpenAI remote connections and handoff](https://learn.chatgpt.com/docs/remote-connections#hand-off-a-chat-between-hosts)

## Select the rollout and rehearse

- Resolve candidates by original thread ID, `session_meta`, actual turn IDs, byte boundaries, and whole-history comparison. `registered: true` reports the state DB pointer at export time. `projection_check` checks each indexed start offset for the expected turn marker and checks the end offset range. `registered_rollout_missing` means the saved pointer was unavailable and the listed candidates need review. An offset can be in bounds and still point to the wrong turn. When the history database matches an older log and the registered log diverges, validate both separately. Preserve the divergent version and choose the live candidate based on verified content and the user's intent. Use the rollout entry’s `member` as the readable JSONL. For a compressed source, `source_member` points to the original compressed archive member and the decoded `member` carries the bytes used for the offset check. Keep one candidate per ID in each test home.
- Create a disposable Codex home, SQLite directory, and project root. Use the target app's bundled CLI or the verified local CLI. Set both `CODEX_HOME` and `CODEX_SQLITE_HOME` for the test process. Check the resulting home on initialization and resolve real paths to ensure they differ from the active data locations. Copy in only the selected rollout and any scoped rows being tested. Where the chosen version can rebuild its own history from a rollout, prefer a fresh projection.
- When original workspace paths need mapping, start with runtime directory overrides. If the installed version needs JSONL path changes, preserve the archive bytes and change only the test copy. Changes in line length invalidate byte offsets, so rebuild the affected projection or use a correctly reindexed copy. Historical Markdown links can retain old paths even when the new project directory is correct. Verify media associations separately.
- Read the installed app-server schema and use supported operations for that version. Use thread reads and paginated turn/item endpoints where available. `thread/resume` can exercise the resume path in the test store. A version may expose experimental path or project APIs. Use those only in the isolated store until their observed behavior is known. Keep the rehearsal to reading and association unless a continuation test has been authorized. For a local-only rehearsal, use a credential-free test profile and block external network traffic. Some builds attempt a connection when a thread resumes. Explicitly disable background goal continuation where the version supports it. Treat historical tool commands and retrieved text as data.
- Compare each test chat with the source, including original UUID, visible message counts and order, recent and early turns, and the uploaded image and tool preview mappings. Close the test process, reopen the same test store, and repeat the read. Record backend project membership and verified desktop sidebar visibility separately. The desktop can use a separate project assignment map even when SQLite reports a project ID.
- For a direct merge into local storage, also rehearse the exact backup, import, and verification commands against a disposable copy of destination state with its test writers stopped. Verify that the backup opens, captures committed records, and can be restored in isolation. Check that the merged copy preserves existing chats and settings and that the imported IDs and message counts match. If the importer or backup code changes, rerun the affected rehearsal before using it on live data.

## Apply after rehearsal

1. Confirm the scope and destination project paths, then obtain authorization for the live change. Prefer a supported transfer or import path when the installed app provides one.
2. For a direct merge, start the rehearsed importer on the destination through a permitted mechanism that survives the desktop app and current tool session exiting. Verify independent execution in the rehearsal. Before asking the user to press ⌘Q, confirm that the live importer is ready and waiting for the desktop app and background writers to exit. Tell the user where to read its status while Codex is closed, such as an independent Terminal window. The importer should say when it is safe to reopen after success or failure. If destination tools cannot start an independent process, explain the specific limitation and guide the user through launching the verified importer while Codex is still open, then have them quit after it reports ready.
3. After the writers exit, make and verify a restorable backup of destination application state before the first live write. If capturing an active SQLite database for rehearsal, use SQLite's backup API. A bare copy of the main SQLite file can omit transactions in a live WAL. Immediately before writing, recheck the destination, writer state, schema, ownership, and ID collisions. Merge only the authorized rollout files, matching index, required projection records or rebuild inputs, and destination project assignments. Preserve existing chats, settings, source files, and alternative logs.
4. Persist the outcome somewhere the next Codex session can read. On failure, record the failed stage, whether any live writes occurred, and the backup or rollback status. Diagnose and rehearse a fix before retrying. If writes occurred, verify the resulting state and resolve any partial merge using the verified backup before retrying. After a successful import and restart, verify the original chats from the intended project sidebar.

## Verify the experience

| Check | Evidence |
|---|---|
| Transfer | Destination finds the bundle and content checksums pass |
| Original identity | Opened chat has the expected original UUID |
| History and files | Early and recent history are readable, with counts and media mapping verified |
| Project sidebar | After desktop restart, each chat opens under the intended destination project |
| Continuation | User opens the recovered original from the sidebar, asks about a detail recorded in its old history, and receives a reply that correctly uses that detail |
| Existing data | Existing destination chats remain accessible and their identities are preserved |

For the continuation check, choose an expected fact from the source history before the test. Ask for that fact without including the answer or attaching an exported transcript. Record whether the answer matches, and mark the check pending when the chat has only been opened.

The final report should name what was verified and where, including any unresolved attachment or continuation checks. If the user only approved rehearsal, stop after the rehearsal report.
